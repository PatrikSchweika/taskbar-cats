# Name Tags Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Holding the pointer over a cat shows its name on a small tag above it.

**Architecture:** The colony finds the cat under the pointer each tick and marks it hovered. A hovered cat holds still, so the tag can be read. A tag controller (`src/core/nameTag.ts`) times the tag and places it through a new `LabelView`, which each platform implements: an `St.Label` on GNOME, a `<div>` on Windows. The overlay stays click-through.

**Tech Stack:** TypeScript on Node 22 (`node --test` with native type stripping), GJS/St and libadwaita on GNOME, Electron 44 on Windows, Biome.

**Spec:** `docs/superpowers/specs/2026-11-16-playful-cats-design.md` (sections "What a cat does, in priority order", "Hover and the name tag", "The name tag", "Settings summary").

## Fitting in with the other three plans

Four plans implement the design: cat play (already implemented), food bowls (already implemented), name tags (this one) and [petting](2026-11-16-petting.md). They can land in any order. They touch the same few places, so every plan follows these rules:

- **The priority chain.** `Cat.update` decides each tick with drive flags (`hunting`, `interested`, `sleepy` today) and one `if / else if` chain that sets `_target`. The design's full order is hunt → purr (`beingPetted`) → hover (`underPointer`) → food (`seekingFood`) → pointer interest (`interested`) → sleep (`sleepy`) → play → wander. Add your flag and branch at your place among the ones that exist. Your flag is false when any flag above it is true. Each existing flag below yours gets `&& !yourFlag`. Branches for new states in the state machine go right after the POUNCE branch, in the same order.
- **Shared building blocks.** Two pieces belong to two plans each: hover (name tags, petting) and the rub detector (petting, food bowls). Each plan that needs one carries the same task for it. If the code already exists, check it against that task's Interfaces block, run that task's tests, and move on.
- **Shared files.** New tests go in new `describe` blocks. New settings, settings rows and README lines go at the stated spot; leave entries from the other plans alone. If two plans are built on parallel branches, expect simple merge conflicts in `cat.ts`, the settings tables, the schema and the README. Keep both sides.

## Global Constraints

- Node `>=22.22.2`. Run one test file with `node --import ./tests/support/hooks.ts --test <file>`. Run everything with `npm run check` (Biome with warnings as errors, `node tools/cli.ts check`, then all tests).
- Format with Biome (tabs). Run `npm run fix` before every commit.
- Imports between source files end in `.js`. Tests import sources with `.ts`.
- Every GSettings key in the schema must appear in the core tables. `tests/core/config.test.ts` fails otherwise.
- Nothing new may be reactive or catch input. GNOME actors use `reactive: false`. Windows elements use `pointer-events: none`.
- User-written names are plain text everywhere: GNOME `St.Label.text` (never markup), Windows `textContent` (never `innerHTML`).
- Positions and sizes inside the simulation are in the positioning space (`cat.size`, not `cat.iconSize`). The pointer arrives in the same space on both platforms.
- The Electron binary isn't installed on the development machine. Windows renderer code is checked by `npm run typecheck` and CI, not by running it.
- Commit messages follow the repository style: one imperative sentence, no prefix. End each one with the `Co-Authored-By` line required for the session.
- Values the spec pins (copy them exactly): tag delay 0.4 s, linger 0.8 s, gap 2 px, max 24 characters plus "…". Look: white 12 px system font on `rgba(20, 20, 20, 0.8)`, 4 px corner radius, 1 px by 6 px padding, no wrapping. Windows name-tag room 24 px.

## Review Focus

1. **A cat removed from the settings while its tag shows.** Expected: the tag hides at once, with no throw. Test: Task 3 "hides the tag when its cat is gone".
2. **Long or odd names** (40 characters, `<b>&amp;</b>`). Expected: the tag shows the text literally, cut to 24 characters plus "…". Tests: Task 3 "cuts long names" and "shows markup literally", Task 4 "sets plain text, never markup".
3. **A 2× HiDPI display.** The hover square must use the on-screen size, so hovering at the cat's visible top still counts. Test: Task 2 "finds a cat at 2x by its on-screen square".
4. **The pointer resting over a cat that would walk to the pointer.** Expected: the hovered cat holds still instead of fanning out away from it. Test: Task 2 "holds still and looks up while the pointer is over it".
5. **A tag over the largest cat on Windows.** Expected: the strip is tall enough that the tag isn't clipped. Test: Task 5 "leaves room for a name tag above the largest cat".

- [ ] **Step 3: Implement**

`NameTag.update`:
- **A hovered cat that isn't the tag's cat:** if the tag is visible, switch to the hovered cat at once. If not, count up hover time and show the tag once it reaches the delay. Hovering a different cat resets the count.
- **Nothing hovered:** count down the linger, and hide the tag when it runs out.
- **The tag's cat is not in `cats`:** hide the tag at once.
- **Setting off:** hide the tag and reset.
- **While visible**, every tick: `setText(tagText(resolveCatName(settings, cat.index)))` and `place(cat.x, floorY - cat.size - NAME_TAG_GAP)`.

`Colony` creates its `NameTag` lazily on the first `update` (`host.createLabelView()`). It calls `tag.update(dt, hovered, this.cats, world.floorY, settings)` after the cats have moved. `destroy()` destroys the tag and sets it back to null.
